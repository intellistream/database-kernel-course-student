# S02.Q09 DML 执行协调

## 这题要解决什么

DML 执行层需要把计划的源行准确交给物理变更端口，并处理重复 RID、部分失败和受影响行数，避免把行流与修改结果混为一谈。

## 开始前读懂什么

ModifyTable 的源行与目标列映射、RID 去重、批量变更的物化边界，以及物理变更端口的错误返回。本题使用的夹具契约见[夹具说明](../fixtures.md)：F-ROWS、F-MUTATION，它们说明验收输入/端口边界，并不意味着仓库中普遍已有同名可直接实例化的类。阅读相关知识只是建立语境，不要求先完成关联题目。

## 先走通一个小例子

UPDATE 的输入流两次给出同一 RID 时，该 RID 只应修改一次；批量中第 3 行失败，报告的影响行数只能计成功变更，且已取得的源行/端口资源仍被正确清理。

先在纸上标出输入、应返回的状态和需要保留的资源；这比一开始扩展到完整工作负载更容易发现边界错位。

## 分步实现

1. 先打开子计划并校验目标 descriptor 与映射。
2. 为 INSERT 逐行计算新值，为 UPDATE/DELETE 先物化并去重 RID。
3. 通过物理端口提交单个变更，收集影响行数和返回状态。
4. 处理中途错误、rescan 与结果行输出，释放临时物化。

每完成一步都回到 marker 附近检查调用方期待的是值、错误还是 guard/自有对象；不要把相邻题的策略或事务规则塞进这里。

## 必须守住的约束

同一 RID 不能在一次操作中重复更新/删除；旧值、新值和目标列不得错位。失败不得虚报影响行数，端口错误要停止或按契约传播，不能继续使用失效行引用。

## 怎样验证

验收必须覆盖以下全部检查：

- 同一 RID 只修改一次
- 批量中途失败
- 影响行数
- 旧新行与目标列映射

现有测试源码可作为场景素材：[modify_table_test.cpp](../../../libs/execution/tests/modify_table_test.cpp)、[query_test.cpp](../../../libs/engine/tests/query_test.cpp)。它们可能跨题，不能替代本题的独立验收。独立注册待补齐；补齐后可在仓库根目录运行 `python3 labs/run.py unit S02.Q09`，并以实际报告为准。可先运行 `python3 labs/run.py list --stage 02` 核对登记状态。
