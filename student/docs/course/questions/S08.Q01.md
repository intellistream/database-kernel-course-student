# S08.Q01 隐式与显式事务状态机

[返回阶段指南](../stages/S08.md)｜[题目总览](../README.md)

验收状态：本题的独立测试登记尚待补齐；现有测试只作素材，F-TXN 是夹具契约名。

## 这题要解决什么

同一条 SQL 在自动提交模式下应成为一个完整事务，而 `BEGIN` 之后的多条命令必须属于同一显式事务。状态机要让命令入口、成功完成、报错、`COMMIT` 与 `ROLLBACK` 对同一状态给出一致决定，避免一次失败把会话悄悄带回可提交状态。

## 开始前读懂什么

阅读 `TransactionStateMachine` 的公开状态、command id 与 epoch 含义；区分“开始命令”和“完成命令”的职责；理解显式事务的 Failed 不是普通 Idle。这里只要求读接口，其他题的实现不是前置条件。

## 从哪里开始

从 [state.cpp](../../../libs/transaction/src/state.cpp) 的 `begin_explicit`、`start_command`、`finish_command`、`commit_explicit` 和 `rollback_explicit` 开始，`preview_finish_command` 与 `apply_*` 显示校验和发布的边界。在仓库根执行 `rg -n 'LAB-S08\.Q01:.*-BEGIN' libs`，只处理该题 marker 包围的区间。

## 先走通一个小例子

设会话初始 Idle。普通命令开始后进入 Implicit，成功完成后回到 Idle 并推进一次命令边界；`BEGIN` 后开始两条命令均保持 Explicit。若第二条失败，观察状态变为 Failed，此时 `COMMIT` 必须被拒绝，而 `ROLLBACK` 后才回到 Idle。

## 分步实现

1. 列出四种状态对 start、finish、BEGIN、COMMIT、ROLLBACK 的允许转换。
2. 先实现不改变状态的校验或预览，再让 apply 函数一次性更新状态和 command/epoch。
3. 让嵌套 `BEGIN` 返回可诊断错误，且不改变原显式事务。
4. 把命令错误显式标记为 Failed，并只为回滚保留恢复出口。

## 实现约束

- 自动提交路径也是本题算法，不能靠默认成功绕过。
- 失败显式事务只能 `ROLLBACK` 后恢复；不得用物理 UNDO 取代既有 MVCC 回滚语义。
- 任何非法命令都不能部分推进 command id、epoch 或状态。

## 怎样验证

逐项覆盖：Idle/Implicit/Explicit/Failed 全状态表、嵌套 BEGIN、失败仅可回滚、完成失败可诊断。阅读并运行现有 [state_test.cpp](../../../libs/transaction/tests/state_test.cpp) 作为素材；独立注册补齐后，可按课程测试导航执行该题 unit 命令。

## 思考题

- 一次命令的“成功结果”是在预览时还是在 apply 后才对外可见？
- 报错发生在显式事务中时，哪一个状态仍能表达“资源还需由回滚收尾”？
