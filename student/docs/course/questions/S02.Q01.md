## 这题要解决什么

SQL 前端需要把第三方解析结果转换成项目可长期持有的 Source AST，并精确保留语句边界和拒绝原因，后续绑定才能安全使用它。

## 开始前读懂什么

第三方解析树的生命周期、Source AST 的自有节点，以及 SQL 文本中引号、注释和多语句边界。本题使用的夹具契约见[夹具说明](../fixtures.md)：F-AST，用于说明输入和依赖端口。

## 从哪里开始

本题源码入口是 [parser.cpp](../../../libs/sql/src/parser.cpp)。优先定位 `parse_sql`、`AstProjector::project_statement_node`、`project_raw_statements`，再从 `expression`、`select_query`、`create_table_statement` 的 marker 进入具体分支。实现范围为本题 marker 包围的区间；在仓库根目录检索：

```sh
rg -n 'LAB-S02\.Q01:.*-BEGIN' libs
```

## 先走通一个小例子

解析一段含标识符、字符串字面量和两个普通语句的文本，应得到两棵独立 AST；释放第三方解析器对象后，AST 内容仍可访问。未支持的语法应带位置地拒绝。

先在纸上标出输入、应返回的状态和需要保留的资源；这比一开始扩展到完整工作负载更容易发现边界错位。

## 分步实现

1. 先验证文本、UTF-8 与语句边界，避免把引号或注释中的分号当分隔符。
2. 把第三方节点投影为自有的标识符、字面量和普通语句节点。
3. 为 SELECT、VALUES、DML、普通 DDL 分支逐一保留源位置。
4. 在未知节点、超出范围的列表和不支持形态上返回明确错误。

每步实现后检查调用方的返回类型、错误和对象生命周期。

## 实现约束

AST 不得借用第三方树或原始缓冲区的易失内存；多语句边界必须精确。集合、连接和子链接不属于本题，不能被悄悄降级成别的语义。

## 怎样验证

检查以下场景：

- 名称与字面量
- 多语句边界
- 错误输入与不支持语法
- 解析器内存释放后 AST 有效

现有测试源码可作为场景素材：[parser_test.cpp](../../../libs/sql/tests/parser_test.cpp)、[parser_corpus_test.cpp](../../../libs/sql/tests/parser_corpus_test.cpp)。测试范围见对应源码。独立注册待补齐；补齐后可在仓库根目录运行 `python3 labs/run.py unit S02.Q01`，并以实际报告为准。可先运行 `python3 labs/run.py list --stage 02` 核对登记状态。

## 思考题

- 解析器释放后，当前节点是否仍指向外部字符串？
- 分号位于字符串或注释时，为什么不能结束语句？
