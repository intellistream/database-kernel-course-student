# S10.Q04 WAL 管理与后台刷盘

[返回阶段指南](../stages/S10.md)｜[题目总览](../README.md)

验收状态：本题的独立测试登记尚待补齐；现有测试只作素材，夹具名只表示契约。

## 这题要解决什么

`WalManager` 将 append 的预留/发布、等待 durable LSN、后台 writer 的批次、唤醒和关闭组织为一个服务。调用方等待的 LSN 只有真正刷盘后才能返回；后台 I/O 错误必须传给等待者，关闭要排空活动操作并允许规定的失败重试。检查点 control 发布是后续题。

## 开始前读懂什么

阅读 manager 的 append/flush API、后台线程的触发条件和活动操作计数；了解 ring 与 writer 的 frontier。不要把管理层的等待条件替换成“写过就算完成”。

## 从哪里开始

从 [manager.cpp](../../../libs/wal/src/manager.cpp) 的 append、flush、生命周期入口开始，配合 [manager_background_writer.cpp](../../../libs/wal/src/manager_background_writer.cpp) 的批次、唤醒和停止逻辑。执行 `rg -n 'LAB-S10\.Q04:.*-BEGIN' libs`。

## 先走通一个小例子

两个调用者 append 不同记录并等待各自末尾 LSN。后台一次批量写入和同步后，低目标与高目标按 durable frontier 醒来；若该批次 sync 失败，二者得到错误而非成功。发起 close 时禁止新 append，允许已在飞操作收尾；一次关闭失败后根据契约仍可重试。

## 分步实现

1. 串起 append 的 reservation、写入、publish 和记录结束 LSN。
2. 为 flush waiter 注册目标，只在 durable frontier 达到时完成。
3. 实现后台批量选择、信号、错误缓存和等待者广播。
4. 管理活动操作、关闭排空和失败后的可重试资源状态。

## 实现约束

- 等待者不得在 written 但未 durable 时早返回。
- 后台错误必须一致传播，不能只让线程悄悄退出。
- 关闭期间不接受新工作，且不能丢弃已发布的 WAL 或卡住等待者。

## 怎样验证

覆盖批量刷盘、等待者不早返回、后台错误传播、关闭排空与失败重试。测试素材：[manager_test.cpp](../../../libs/wal/tests/manager_test.cpp)、[manager_background_writer_test.cpp](../../../libs/wal/tests/manager_background_writer_test.cpp)、[wal_durability_test.cpp](../../../libs/recovery/tests/wal_durability_test.cpp)；独立注册待补齐。

## 思考题

- 两个不同目标的等待者为何可由同一个批次正确唤醒？
- I/O 错误已发生时，新来的 waiter 应观察到哪种状态？
