# S01.Q05 脏页回写与批次跟踪

**验收状态：**本题的 LAB 区间已挖空，但独立测试注册仍待补齐；当前运行 `unit` 的“未执行”不能视为通过。

## 这题要解决什么

页面修改不能因崩溃或并发回写丢失；回写必须遵守 WAL 先行，并区分这次镜像与之后的新修改。checkpoint 也依赖这套精确脏页跟踪。

## 开始前读懂什么

脏页 generation、Frame 的 I/O 声明、WAL 先行规则，以及 checkpoint 脏集合与普通刷盘的差别。本题使用的夹具契约见[夹具说明](../fixtures.md)：F-BUFFER、F-WAL，它们说明验收输入/端口边界，并不意味着仓库中普遍已有同名可直接实例化的类。阅读相关知识只是建立语境，不要求先完成关联题目。

## 先走通一个小例子

一页被修改后请求回写：WAL 端口先达到该页的 LSN，随后才写数据页。写失败后该页仍为脏；写进行期间再次修改，旧回写完成不能清掉新一代的脏标记。

先在纸上标出输入、应返回的状态和需要保留的资源；这比一开始扩展到完整工作负载更容易发现边界错位。

## 分步实现

1. 先用稳定页镜像和 generation 标识一次具体写回。
2. 在数据页写前请求 WAL 持久化到所需 LSN。
3. 写成功时仅在 generation 仍匹配时清脏，并结束 I/O 状态。
4. 把 checkpoint 标记与批次选择接上，确保普通刷盘和 checkpoint 选择均可重试。

每完成一步都回到 marker 附近检查调用方期待的是值、错误还是 guard/自有对象；不要把相邻题的策略或事务规则塞进这里。

## 必须守住的约束

数据页不得越过其 WAL 持久化点；写失败保持脏且可重试。I/O guard 必须成对结束；并发再脏不能被旧镜像的完成路径抹掉。

## 怎样验证

验收必须覆盖以下全部检查：

- WAL 先于数据页
- 写失败仍为脏
- 并发再脏不能被旧回写清除

现有测试源码可作为场景素材：[buffer_pool_test.cpp](../../../libs/storage/tests/buffer_pool_test.cpp)。它们可能跨题，不能替代本题的独立验收。独立注册待补齐；补齐后可在仓库根目录运行 `python3 labs/run.py unit S01.Q05`，并以实际报告为准。可先运行 `python3 labs/run.py list --stage 01` 核对登记状态。
