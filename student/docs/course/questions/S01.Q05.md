# S01.Q05 脏页回写与批次跟踪

## 这题要解决什么

页面修改不能因崩溃或并发回写丢失；回写必须遵守 WAL 先行，并区分这次镜像与之后的新修改。checkpoint 也依赖这套精确脏页跟踪。

## 开始前读懂什么

脏页 generation、Frame 的 I/O 声明、WAL 先行规则，以及 checkpoint 脏集合与普通刷盘的差别。本题使用的夹具契约见[夹具说明](../fixtures.md)：F-BUFFER、F-WAL，用于说明输入和依赖端口。

## 从哪里开始

本题源码入口是 [buffer_pool.cpp](../../../libs/storage/src/buffer_pool.cpp)、[frame.cpp](../../../libs/storage/src/frame.cpp)。优先定位 `BufferPool::Impl::writeback_image`、`writeback`、`flush_checkpoint_batch`、`mark_checkpoint_dirty`，并查看 `Frame::begin_io`、`finish_io`、`next_generation`。实现范围为本题 marker 包围的区间；在仓库根目录检索：

## 先走通一个小例子

一页被修改后请求回写：WAL 端口先达到该页的 LSN，随后才写数据页。写失败后该页仍为脏；写进行期间再次修改，旧回写完成不能清掉新一代的脏标记。

先在纸上标出输入、应返回的状态和需要保留的资源；这比一开始扩展到完整工作负载更容易发现边界错位。

## 分步实现

1. 先用稳定页镜像和 generation 标识一次具体写回。
2. 在数据页写前请求 WAL 持久化到所需 LSN。
3. 写成功时仅在 generation 仍匹配时清脏，并结束 I/O 状态。
4. 把 checkpoint 标记与批次选择接上，确保普通刷盘和 checkpoint 选择均可重试。

每步实现后检查调用方的返回类型、错误和对象生命周期。

## 实现约束

数据页不得越过其 WAL 持久化点；写失败保持脏且可重试。I/O guard 必须成对结束；并发再脏不能被旧镜像的完成路径抹掉。

## 怎样验证

检查以下场景：

- WAL 先于数据页
- 写失败仍为脏
- 并发再脏不能被旧回写清除

现有测试源码可作为场景素材：[buffer_pool_test.cpp](../../../libs/storage/tests/buffer_pool_test.cpp)。测试范围见对应源码。独立注册待补齐；补齐后可在仓库根目录运行 `python3 labs/run.py unit S01.Q05`，并以实际报告为准。可先运行 `python3 labs/run.py list --stage 01` 核对登记状态。

## 思考题

- 如何区分“这次镜像已写完”和“页面此后又被改过”？
- 写回失败后，哪些状态应恢复、哪些状态应保留？
