# S08.Q04 锁兼容与等待队列

[返回阶段指南](../stages/S08.md)｜[题目总览](../README.md)

验收状态：本题的独立测试登记尚待补齐；现有测试只作素材，F-GRAPH、F-TXN 是夹具契约名。

## 这题要解决什么

表锁和行锁必须把兼容请求立即授予，把冲突请求按队列保留，并在释放、升级、取消时让合格等待者准确醒来。这里的难处不只是兼容矩阵，还包括一个请求在等待期间的所有权和队列位置，避免取消或完成事务留下无法唤醒的请求。

## 开始前读懂什么

阅读表/行锁模式、subsumes 的含义，以及 lock owner、request、target 三种状态的关系。了解等待图会读取队列，但环检测本身是下一题；无须先实现它。

## 从哪里开始

从 [lock_mode_policy.cpp](../../../libs/transaction/src/lock_mode_policy.cpp) 的兼容与覆盖判断开始，再读 [lock_queue.cpp](../../../libs/transaction/src/lock_queue.cpp) 的授予、撤销和释放，最后接入 [lock_manager.cpp](../../../libs/transaction/src/lock_manager.cpp) 的 `acquire`、`grant_waiters`、`cancel_wait`、`release_all`。命令：`rg -n 'LAB-S08\.Q04:.*-BEGIN' libs`。

## 先走通一个小例子

事务 A 已持有与读兼容的锁，事务 B 申请同类锁应立即成功；事务 C 申请冲突锁应入队。A、B 依次释放后，C 才被授予。若 C 在等待时取消，随后释放不能再唤醒它，也不能阻塞队列后方兼容请求。

## 分步实现

1. 完成模式合法性、兼容和覆盖关系的纯判断。
2. 实现队列中 holders 与 waiters 的兼容扫描和公平顺序。
3. 接入立即授予、入队等待、升级和 owner 记录。
4. 实现取消、事务结束、目标回收和全部必要的唤醒。

## 实现约束

- 覆盖已有锁的请求不能重复制造等待项。
- 取消与升级必须清除等待记录，释放后不得丢失一次应有唤醒。
- 表锁和行锁只接受各自合法模式；队列状态由受保护的所有权维护。

## 怎样验证

覆盖兼容/冲突组合、取消与升级、等待顺序、释放后不丢失唤醒。现有素材为 [lock_manager_test.cpp](../../../libs/transaction/tests/lock_manager_test.cpp) 与 [lock_queue_test.cpp](../../../libs/transaction/tests/lock_queue_test.cpp)；独立注册待补齐。

## 思考题

- 释放一个 holder 后，哪些排队请求可以一起授予，哪些仍必须等待？
- 请求取消后，owner、target 与等待图各自还保留了什么？

## 延伸阅读

实现时把“是否可授予”的纯判断与“把请求写入队列”的副作用分开检查会更容易定位问题：前者应可反复计算，后者必须只发生一次并受到同一把状态锁保护。
