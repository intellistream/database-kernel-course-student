# S10.Q07 普通检查点与 control 发布

[返回阶段指南](../stages/S10.md)｜[题目总览](../README.md)

验收状态：本题的独立测试登记尚待补齐；现有测试只作素材，夹具名只表示契约。

## 这题要解决什么

普通（fuzzy）CHECKPOINT 允许并发事务继续：它捕获边界、排空恰当的脏页/CLOG/目录批次，写入最终 checkpoint 记录并耐久，然后才发布新的 control 代和回收旧 WAL。并发期间页面可再脏，失败时旧 control 仍是权威。本题不处理静态 checkpoint 的接纳与排空，那是 S10.Q08。

## 开始前读懂什么

阅读 checkpoint coordinator、control store 的双代/校验契约、WAL durable frontier 和页面 durability。核对 [control_format.cpp](../../../libs/wal/src/control_format.cpp)：有效 control 若有 checkpoint，必须满足 `redo_lsn <= checkpoint_lsn`；不要采用“redo 不能早于 checkpoint”的错误说法。

## 从哪里开始

从 [checkpoint.cpp](../../../libs/recovery/src/checkpoint.cpp) 的协调顺序、[manager_checkpoint.cpp](../../../libs/wal/src/manager_checkpoint.cpp) 与 [manager.cpp](../../../libs/wal/src/manager.cpp) 的记录/回收，及 [control_store.cpp](../../../libs/wal/src/control_store.cpp) 和 [database.cpp](../../../libs/engine/src/database.cpp) 的发布入口开始。命令：`rg -n 'LAB-S10\.Q07:.*-BEGIN' libs`。

## 先走通一个小例子

捕获检查点开始边界后，某页被刷写又被并发事务重新弄脏；本轮只确认捕获批次的耐久义务，不把再脏误称已覆盖。所有数据/CLOG/目录要求满足后，写最终 checkpoint WAL 并 flush；仅此成功后发布含合法 redo/checkpoint LSN 的 control。任一步失败，重开仍使用旧 control，旧 WAL 不可过早回收。

## 分步实现

1. 捕获 fuzzy 边界和需要完成的脏页、CLOG、目录批次。
2. 按 WAL 先于数据的约束排空各持久化义务，并识别再脏。
3. 生成并耐久最终 checkpoint 记录，再原子发布 control 新代。
4. 只在新 control 可验证后回收不再需要的 WAL；为每个失败点保留可重试状态。

## 必须守住的约束

- 并发再脏不等于本轮失败，也不能被当作已持久化的新状态。
- 最终记录 → control → 回收顺序不可倒置；旧/新 control 的权威边界清晰。
- control 校验要求有效 `redo_lsn <= checkpoint_lsn`；无 checkpoint 时 redo 必须无效。

## 怎样验证

覆盖并发再脏、各发布失败点、旧/新 control 权威边界、过早回收禁止。测试素材是 [checkpoint_test.cpp](../../../libs/recovery/tests/checkpoint_test.cpp)、[control_store_test.cpp](../../../libs/wal/tests/control_store_test.cpp)、[manager_test.cpp](../../../libs/wal/tests/manager_test.cpp)；独立注册待补齐。

## 卡住时先想这几个问题

- 若 control 已发布而最终 checkpoint WAL 尚未 durable，重开从哪里开始？
- 页面再次变脏后，为什么本轮 checkpoint 仍可合法完成？

## 延伸阅读

审查失败路径时，用“当前 control 能否独自指导下一次 open”作判断标准。若答案不能明确给出旧还是新代以及对应 redo 起点，就说明某个耐久或发布步骤被放在了错误位置。
